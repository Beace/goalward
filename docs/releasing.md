# Releasing Goalward for macOS

Goalward publishes macOS universal prereleases in batches, not on every Pull Request merge. The local Codex daily Goalward release automation dispatches the GitHub Actions release workflow on `main` at **14:00 Asia/Shanghai**; a maintainer can also run the same workflow manually. The workflow itself has no GitHub cron trigger and skips the build and Release when there are no unreleased commits. The published GitHub Release, its version tag, and the tagged Git commit are the release source of truth. No person or workflow pushes changes directly to `main`.

## Develop through a Pull Request

1. Fetch the latest `main`, create a fresh task branch (Codex uses `codex/<task-name>`), and make the change there.
2. Give the PR a Conventional Commit title that accurately describes its effect: `feat:` for a feature, `fix:` for a fix, or another readable type such as `docs:`, `ci:`, or `chore:`. Mark incompatible changes with `!` (for example, `feat!:`) or `BREAKING CHANGE:` in the squash commit body.
3. Push only the task branch, open a PR, check its CI, and squash-merge it. PR CI runs the frontend, Rust, and release-tooling unit tests; it does **not** build the App, DMG, or ZIP. GitHub's `main` ruleset requires the `frontend-tests`, `rust-tests`, and `release-tooling` checks, plus a PR; the repository only allows squash merges. If those job names change, update the ruleset too. The squash commits on `main` become inputs to the next release; merging a PR does **not** publish one immediately.

## Automatic version and changelog

The workflow takes a snapshot of `main` and compares it with the most recent **published** SemVer Release and its verified Git tag. Until there is a published Release, it uses the recorded 0.1.1 baseline commit in `.github/release-baseline.json`. Drafts do not advance the version. If the selected commit is already released, is older than the last released commit, or there are no new commits, the workflow succeeds without building or creating a Release.

For all new squash commits in that range, a breaking change calls for a major bump, `feat:` a minor bump, and any other title a patch bump. The **highest bump across the batch is applied once** to the previous published version; an unrecognized title is treated as a patch rather than silently skipped. For example, a `feat:` and a `fix:` merged before the daily run produce one minor release containing both changes, not two releases.

The automation-triggered or manually triggered release workflow checks out the selected `main` commit, computes the batch version, builds a universal app for Apple Silicon and Intel, and verifies the app's internal version, DMG, ZIP, signed updater archive, metadata, and SHA-256 checksums. It then explicitly creates a version tag at that **same mainline source commit**, reads the remote tag back, and creates the GitHub prerelease only if the tag matches; the Release command is not allowed to invent a tag from the default branch head. The verified tag—not the Release API's `target_commitish` metadata—is the source of truth for the released commit. Its “What's Changed” list contains **every** included Git commit title with the associated PR author and number. “Full Changelog” compares the previous published tag (or the baseline commit if that tag does not exist) with the new tag. [GitHub Releases](https://github.com/Beace/goalward/releases) is the changelog for versions after 0.1.1; the repository's `CHANGELOG.md` retains the pre-automation 0.1.1 entry.

The version fields in `package.json`, `package-lock.json`, Tauri configuration, `Cargo.toml`, and `Cargo.lock` are a development-build baseline on `main`. The release job deterministically stamps its calculated version into those files **only in the checked-out build workspace**, checks they agree, and records the original Git SHA in `BUILD-INFO.json`. A release tag points to the selected `main` source commit, not to a version-bump commit. To reproduce its app version from a tag, check out the tag, use Python 3.11 or later to run `python3 scripts/release.py stamp X.Y.Z` with the tag's version, install from the public npm registry with `npm ci --registry=https://registry.npmjs.org`, then build on an Apple Silicon Mac with `npm run mac:dist`. Do not claim that an unstamped checkout of the tag already contains its release version.

The existing `v0.1.1` draft prerelease has no Git tag and is kept untouched. It is not a published Release and does not move the baseline. For the first published batch, the Full Changelog comparison starts at the recorded baseline commit.

## Signed updates

Each new release includes the universal `Goalward_X.Y.Z_macos-universal.app.tar.gz`, its `.sig` file, and `latest.json`, alongside the DMG and ZIP. The manifest contains `darwin-aarch64` and `darwin-x86_64`, both pointing to the same universal archive through a URL with that release's explicit `vX.Y.Z` tag. The manifest embeds the signature's **content**, not a path to the `.sig` file. Its notes link to the full commit-based GitHub Release notes. `BUILD-INFO.json` records the updater public-key fingerprint and signed version; `SHA256SUMS.txt` covers all five payload files, including the manifest and signature.

The GitHub Release copy of `latest.json` keeps `https://github.com/Beace/goalward/releases/download/vX.Y.Z/...` package URLs. The app tries `https://releases.goalward.dev/latest.json` first. That manifest is a rewritten copy whose package URLs point at `https://releases.goalward.dev/vX.Y.Z/...`. If the R2 manifest cannot be read or does not match the versioned R2 object, the app falls back to the existing prerelease-aware GitHub discovery: the paginated Releases API, then that release's `latest.json` asset. A reachable R2 manifest is authoritative, including when it announces no newer version, so a normal check does not call the GitHub API. Do not use GitHub's `/releases/latest` or `/releases/latest/download/latest.json` as that fallback: GitHub excludes prereleases from that selection. `plugins.updater.endpoints` still lists that static GitHub URL second so the plugin configuration shows the same priority; the update command replaces it with the selected release asset. The updater public key and `requireSignedVersion` are unchanged. A release without updater assets, including older DMG/ZIP-only releases, cannot be installed through the updater. Older app builds that predate updater support require one manual installation of an updater-enabled DMG or ZIP. Builds that predate the R2 endpoint still check GitHub until they install a build that contains this client.

### Cloudflare R2

Updater downloads are hosted in the existing R2 bucket `goalward-releases` (Cloudflare account `98775cbe093085ec17c5fab233cd571f`). The public custom domain `https://releases.goalward.dev` serves bucket keys from the root. The S3 API endpoint is `https://98775cbe093085ec17c5fab233cd571f.r2.cloudflarestorage.com`. This repository does not create the bucket, domain, or API token.

The release workflow uploads after the GitHub Release is verified, using a pinned AWS CLI (`awscli==1.46.1` in a temporary virtualenv) and `aws s3api put-object --endpoint-url`. Versioned objects are uploaded first. The top-level manifest is uploaded last, so that pointer changes only after the versioned files exist:

| Object key | Cache-Control | Body |
| --- | --- | --- |
| `vX.Y.Z/Goalward_X.Y.Z_macos-universal.app.tar.gz` | `public, max-age=31536000, immutable` | signed updater archive |
| `vX.Y.Z/Goalward_X.Y.Z_macos-universal.app.tar.gz.sig` | `public, max-age=31536000, immutable` | minisign signature file |
| `vX.Y.Z/Goalward_X.Y.Z_macos-universal.dmg` | `public, max-age=31536000, immutable` | manual DMG download for that version |
| `vX.Y.Z/latest.json` | `public, max-age=31536000, immutable` | manifest whose `url` fields use `https://releases.goalward.dev/vX.Y.Z/...` |
| `latest.json` | `public, max-age=60` | the same rewritten manifest |

The release workflow always publishes the top-level `latest.json` for the version it just verified. A backfill always writes the versioned keys, including `vX.Y.Z/latest.json`. It publishes the top-level `latest.json` only when the tag is the newest published GitHub Release, including prereleases, or when the workflow input `update_latest` is `true`. `update_latest: false` leaves that pointer unchanged. The default input is `auto`. The newest release is the first result of `gh release list` (drafts excluded). Do not use GitHub's `/releases/latest` for that comparison: this repository publishes prereleases, and that endpoint omits them. R2 does not store a second copy of the DMG at `download/Goalward.dmg`.

### Stable DMG redirect

`https://releases.goalward.dev/download/Goalward.dmg` is the stable macOS download. The same redirect is available at `/download/latest` and `/download/macos`. A Cloudflare Worker in [workers/download-redirect/](../workers/download-redirect/) handles `releases.goalward.dev/download/*` on the zone `goalward.dev`. R2 custom domains cannot send redirects, so the Worker reads `https://releases.goalward.dev/latest.json`, caches that response at the edge for 60 seconds (`cf.cacheTtl` and `cacheEverything`, because Cloudflare does not cache JSON by default), and responds `302` to `https://releases.goalward.dev/vX.Y.Z/Goalward_X.Y.Z_macos-universal.dmg` with `Cache-Control: public, max-age=60`. The versioned DMG keeps its immutable cache. If the manifest cannot be read or its version is not `X.Y.Z`, the Worker responds `302` to `https://github.com/Beace/goalward/releases` with `Cache-Control: no-store`. Any other `/download/*` path responds `404`.

The Worker reads `latest.json` on each request, so it is deployed once rather than on every release. Run **Actions → Deploy download redirect Worker** on `main` after the token below is set. The workflow installs Wrangler `4.151.2` and runs `wrangler deploy`. It logs a warning and exits successfully when `CLOUDFLARE_API_TOKEN` is missing, and it does not print the token. The account id `98775cbe093085ec17c5fab233cd571f` is in `workers/download-redirect/wrangler.toml`. Until this route is deployed, the stable URL is not a redirect. The route is only `/download/*`, so `latest.json` and the versioned objects stay on R2.

Create the API token on that account and limit the zone scope to `goalward.dev`:

| Scope | Permission | Why |
| --- | --- | --- |
| Account | Workers Scripts: Edit | Deploy an existing Worker. Legacy name for Workers Editor. |
| Account | Workers Admin | Required for the first `wrangler deploy`, which creates the Worker. Editor cannot create a Worker that does not exist yet. |
| Zone `goalward.dev` | Workers Routes: Edit | Attach `releases.goalward.dev/download/*`. |
| Zone `goalward.dev` | Zone: Read | Wrangler resolves `zone_name` to a zone id. |
| Account | Account Settings: Read | Wrangler reads the account during authentication. |
| User | User Details: Read | Wrangler identifies the token. |
| User | Memberships: Read | Wrangler confirms the token can access the account. |

Do not grant Workers KV, R2, or other zone permissions. This Worker has no bindings.

There is no separate update channel in this repository, so `stable/latest.json` is not published. The ZIP, checksums, build metadata, and installation guide stay on the GitHub Release only. The GitHub `latest.json` bytes are not modified, so `SHA256SUMS.txt` still matches that copy.

Set the repository variable `R2_ACCOUNT_ID` to the Cloudflare account id. When that variable is empty, the workflow uses the `R2_ACCOUNT_ID` secret instead. `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` are repository secrets only. Optionally set the repository variable `R2_BUCKET` (default `goalward-releases`). The release upload and the backfill workflow pass the account id, access key, and secret through the step environment and do not print them. The release workflow logs a warning and continues when the account id, access key, and secret are all absent, so forks and pull-request builds do not fail. A partial set fails the upload. An upload failure after the GitHub Release exists leaves GitHub as the fallback; rerunning the release workflow uploads again without rebuilding when the published assets already match.

To backfill an existing release, run **Actions → Backfill Cloudflare R2 release** on `main` after the account-id variable (or its secret fallback) and the two key secrets are set. The default tag is `v0.5.1`. The workflow downloads that release's updater archive, signature, DMG, and `latest.json`, rewrites only the manifest package URLs, and writes the layout above. With `update_latest` left on `auto`, a tag older than the newest GitHub Release does not replace the top-level `latest.json`. Re-run the workflow on the newest tag when that pointer should move. It fails if those values are missing. The stable DMG URL is the Worker redirect above; backfill does not upload `download/Goalward.dmg`. Installed apps that still embed the GitHub-only checker need one successful update or a manual DMG install before they request `releases.goalward.dev`.

Tauri updater signatures use a persistent private key distinct from Apple's code-signing identity. The public key is committed in `src-tauri/tauri.conf.json` under `plugins.updater.pubkey`; `requireSignedVersion: true` also requires the artifact's cryptographically signed version to match the manifest. The private key must stay outside the repository and must be backed up securely. Losing it prevents the already installed apps from trusting future releases. Do not generate a replacement key on every run or replace the committed public key as a routine release step. [Tauri updater signing documentation](https://v2.tauri.app/plugin/updater/#signing-updates) describes the key format and installation verification.

For a new repository's initial setup, generate the key once in a private directory with the pinned project CLI, put the generated `.pub` **content** into Tauri configuration, and add the private key content as the GitHub Actions secret `TAURI_SIGNING_PRIVATE_KEY`. For example, after checking that no existing signing key must be retained:

```sh
umask 077
mkdir -p ~/.config/goalward/updater
npm run tauri -- signer generate -w ~/.config/goalward/updater/goalward.key -p ''
gh secret set TAURI_SIGNING_PRIVATE_KEY --repo Beace/goalward < ~/.config/goalward/updater/goalward.key
```

The CLI refuses to overwrite an existing key by default; keep that protection. For an encrypted key, set `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` as another repository secret. An unencrypted key uses the empty password. Never paste the private key into a PR, logs, configuration, shell arguments, or a tracked `.env` file.

Release builds explicitly receive these secrets and run `npm run mac:dist -- --updater`, enabling Tauri's `createUpdaterArtifacts` through a build-only configuration override. Before the expensive build, the packaging script signs a temporary probe and verifies it against the committed public key. A missing key, wrong password, or key mismatch stops the release. It then verifies the actual updater archive's artifact and trusted-comment signatures, checks the signed version, extracts the exact verified bytes, verifies the app's macOS signature, and confirms that its contents match the app in the DMG and ZIP. The Linux publication job independently verifies the archive signature, manifest URLs, platform entries, metadata, and checksums before creating the release tag. A changed or unsigned artifact is never published as an automatic update.

Ordinary `npm run mac:dev`, `npm run mac:build`, and `npm run mac:dist` need no updater private key. To validate a signed local universal distribution without publishing it, export `TAURI_SIGNING_PRIVATE_KEY` as the existing key's path or content, optionally export its password, and run `npm run mac:dist -- --updater`. `--updater` requires a fresh universal build and cannot be combined with either repackaging option. A distribution that already contains a signed updater is also protected against media-only repackaging: retain its original verified assets or make a fresh signed build. A fresh local build without `--updater` produces only the manual-installation distribution and removes stale updater files from that version's local output directory. Reproduction of a tagged release still requires the version-stamping step above. Neither local validation nor merging a PR creates a Release or tag.

Updater signature verification establishes the update artifact's source and integrity. Current apps still use ad-hoc macOS signing and are **not Apple-notarized**; the updater does not establish Developer ID, notarization, stapling, or Gatekeeper acceptance. Validate a real installed-app upgrade separately before claiming that end-to-end installation has passed.

## Publish and recover

Use **Actions → Publish macOS universal prerelease → Run workflow** on `main` to request a release before the next 14:00 check. Manual and automation-triggered runs use the same version and verification rules. The workflow serializes release runs; a delayed run targeting a commit already covered by a newer published release is a no-op. New commits merged after a run takes its snapshot wait for the next run.

After verifying the build, the workflow creates a lightweight Git tag through GitHub's refs API at the selected `main` commit, without force-moving any existing tag. It then creates a draft Release only for that verified tag, uploads the eight distribution assets without overwriting existing files, and reads their digests and sizes back from GitHub. The set is the DMG, ZIP, updater archive, updater signature, `latest.json`, `SHA256SUMS.txt`, `BUILD-INFO.json`, and `INSTALL.txt`. It publishes the prerelease only when the complete set matches the verified build. A matching **empty** draft or a tag left behind before draft creation can be retried when its tag still points to the exact planned `main` commit. If any draft asset was already uploaded, or an unfinished draft's tag targets a different commit, preflight stops before another Mac build: rebuilding creates new timestamps and cannot safely reuse the old asset checksums. Inspect the draft and its original Actions run, then manually complete or clean up that draft and its tag before requesting another run. The automation never deletes or replaces draft assets. No DMG, ZIP, or other release binary is committed to Git.

Each public prerelease is currently ad-hoc signed and **not Apple-notarized**. The README and installation guide disclose this limitation. Developer ID signing, notarization, and stapling remain separate work; do not describe these trial builds as notarized or as a final macOS distribution.

If a release fails, inspect its Actions run, tag, and draft before rerunning. A tag left behind before draft creation can be reused only at the same selected `main` commit; a tag pointing elsewhere blocks publication. An empty draft for an older source commit can be resumed by rerunning that original Actions run. For a partially uploaded draft, decide explicitly whether to finish publishing from the original verified artifact or remove the unfinished draft and associated tag before starting a fresh run; do not delete or overwrite assets merely to hide a mismatch. The successful release build is an Actions artifact for diagnosis; the verified GitHub Release assets remain the fallback user downloads, and the R2 objects above are what current updater builds fetch first.

The 14:00 trigger is a local Codex automation attached to the maintainer's task, not a GitHub-hosted schedule stored in this repository. The maintainer's Mac must be powered on with the ChatGPT desktop app running ([Scheduled tasks](https://learn.chatgpt.com/docs/automations)), and GitHub authentication must be available. If the automation does not dispatch the workflow, use the manual workflow after checking the Actions status. No commit is lost from the next successful batch because the range always starts at the last published Release.
