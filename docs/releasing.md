# Releasing Goalward for macOS

Goalward publishes macOS universal prereleases in batches, not on every Pull Request merge. The local Codex automation **Goalward 每日下午发布** dispatches the GitHub Actions release workflow on `main` at **14:00 Asia/Shanghai**; a maintainer can also run the same workflow manually. The workflow itself has no GitHub cron trigger and skips the build and Release when there are no unreleased commits. The published GitHub Release, its version tag, and the tagged Git commit are the release source of truth. No person or workflow pushes changes directly to `main`.

## Develop through a Pull Request

1. Fetch the latest `main`, create a fresh task branch (Codex uses `codex/<task-name>`), and make the change there.
2. Give the PR a Conventional Commit title that accurately describes its effect: `feat:` for a feature, `fix:` for a fix, or another readable type such as `docs:`, `ci:`, or `chore:`. Mark incompatible changes with `!` (for example, `feat!:`) or `BREAKING CHANGE:` in the squash commit body.
3. Push only the task branch, open a PR, check its CI, and squash-merge it. PR CI runs the frontend, Rust, and release-tooling unit tests; it does **not** build the App, DMG, or ZIP. GitHub's `main` ruleset requires the `frontend-tests`, `rust-tests`, and `release-tooling` checks, plus a PR; the repository only allows squash merges. If those job names change, update the ruleset too. The squash commits on `main` become inputs to the next release; merging a PR does **not** publish one immediately.

## Automatic version and changelog

The workflow takes a snapshot of `main` and compares it with the most recent **published** SemVer Release and its verified Git tag. Until there is a published Release, it uses the recorded 0.1.1 baseline commit in `.github/release-baseline.json`. Drafts do not advance the version. If the selected commit is already released, is older than the last released commit, or there are no new commits, the workflow succeeds without building or creating a Release.

For all new squash commits in that range, a breaking change calls for a major bump, `feat:` a minor bump, and any other title a patch bump. The **highest bump across the batch is applied once** to the previous published version; an unrecognized title is treated as a patch rather than silently skipped. For example, a `feat:` and a `fix:` merged before the daily run produce one minor release containing both changes, not two releases.

The automation-triggered or manually triggered release workflow checks out the selected `main` commit, computes the batch version, builds a universal app for Apple Silicon and Intel, and verifies the app's internal version, DMG, ZIP, signed updater archive, metadata, and SHA-256 checksums. It then explicitly creates a version tag at that **same mainline source commit**, reads the remote tag back, and creates the GitHub prerelease only if the tag matches; the Release command is not allowed to invent a tag from the default branch head. The verified tag—not the Release API's `target_commitish` metadata—is the source of truth for the released commit. Its “What's Changed” list contains **every** included Git commit title with the associated PR author and number. “Full Changelog” compares the previous published tag (or the baseline commit if that tag does not exist) with the new tag. [GitHub Releases](https://github.com/Beace/goalward/releases) is the changelog for versions after 0.1.1; the repository's `CHANGELOG.md` retains the pre-automation 0.1.1 entry.

The version fields in `package.json`, `package-lock.json`, Tauri configuration, `Cargo.toml`, and `Cargo.lock` are a development-build baseline on `main`. The release job deterministically stamps its calculated version into those files **only in the checked-out build workspace**, checks they agree, and records the original Git SHA in `BUILD-INFO.json`. A release tag points to the selected `main` source commit, not to a version-bump commit. To reproduce its app version from a tag, check out the tag, use Python 3.11 or later to run `python3 scripts/release.py stamp X.Y.Z` with the tag's version, install from the public npm registry with `npm ci --registry=https://registry.npmjs.org`, then build on an Apple Silicon Mac with `npm run mac:dist`. Do not claim that an unstamped checkout of the tag already contains its release version.

The existing `v0.1.1` draft prerelease has no Git tag and is kept untouched. It is not a published Release and does not move the baseline. For the first published batch, the Full Changelog comparison starts at the recorded baseline commit.

## Signed updates from GitHub Releases

Each new release includes the universal `Goalward_X.Y.Z_macos-universal.app.tar.gz`, its `.sig` file, and `latest.json`, alongside the DMG and ZIP. The manifest contains `darwin-aarch64` and `darwin-x86_64`, both pointing to the same universal archive through a URL with that release's explicit `vX.Y.Z` tag. The manifest embeds the signature's **content**, not a path to the `.sig` file. Its notes link to the full commit-based GitHub Release notes. `BUILD-INFO.json` records the updater public-key fingerprint and signed version; `SHA256SUMS.txt` covers all five payload files, including the manifest and signature.

The native app discovers published Releases using GitHub's paginated Releases API so it can receive the project's prereleases. A release without updater assets, including older DMG/ZIP-only releases, cannot be installed through the updater. Do not use GitHub's `/releases/latest` or `/releases/latest/download/latest.json` endpoint here: GitHub excludes prereleases from that selection. The app follows the selected release's `latest.json` asset and verifies its version and platform entries before offering the update. Older app builds that predate this feature require one manual installation of an updater-enabled DMG or ZIP.

Tauri updater signatures use a persistent private key distinct from Apple's code-signing identity. The public key is committed in `src-tauri/tauri.conf.json` under `plugins.updater.pubkey`; `requireSignedVersion: true` also requires the artifact's cryptographically signed version to match the manifest. The private key must stay outside the repository and must be backed up securely. Losing it prevents the already installed apps from trusting future releases. Do not generate a replacement key on every run or replace the committed public key as a routine release step. [Tauri updater signing documentation](https://v2.tauri.app/plugin/updater/#signing-updates) describes the key format and installation verification.

For a new repository's initial setup, generate the key once in a private directory with the pinned project CLI, put the generated `.pub` **content** into Tauri configuration, and add the private key content as the GitHub Actions secret `TAURI_SIGNING_PRIVATE_KEY`. For example, after checking that no existing signing key must be retained:

```sh
umask 077
mkdir -p ~/.config/goalward/updater
npm run tauri -- signer generate -w ~/.config/goalward/updater/goalward.key -p ''
gh secret set TAURI_SIGNING_PRIVATE_KEY --repo Beace/goalward < ~/.config/goalward/updater/goalward.key
```

The CLI refuses to overwrite an existing key by default; keep that protection. For an encrypted key, set `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` as another repository secret. An unencrypted key uses the empty password. Never paste the private key into a PR, logs, configuration, shell arguments, or a tracked `.env` file.

Release builds explicitly receive these secrets and run `npm run mac:dist -- --updater`, enabling Tauri's `createUpdaterArtifacts` through a build-only configuration override. Before the expensive build, the packaging script signs a temporary probe and verifies it against the committed public key. A missing key, wrong password, or key mismatch stops the release. It then verifies the actual updater archive's artifact and trusted-comment signatures, checks the signed version, extracts the exact verified bytes, verifies the app's macOS signature, and confirms that its contents match the app in the DMG and ZIP. The Linux publication job independently verifies the archive signature, manifest URLs, platform entries, metadata, and checksums before creating the release tag. A changed or unsigned artifact is never published as an automatic update.

Ordinary `npm run mac:dev`, `npm run mac:build`, and `npm run mac:dist` need no updater private key. To validate a signed local universal distribution without publishing it, export `TAURI_SIGNING_PRIVATE_KEY` as the existing key's path or content, optionally export its password, and run `npm run mac:dist -- --updater`. `--updater` requires a fresh universal build and cannot be combined with either repackaging option. A distribution that already contains a signed updater is also protected against media-only repackaging: retain its original verified assets or make a fresh signed build. A fresh local build without `--updater` produces only the manual-installation distribution and removes stale updater files from that version's local output directory. Reproduction of a tagged release still requires the version-stamping step above. Neither local validation nor merging a PR creates a Release or tag.

Updater signature verification establishes the update artifact's source and integrity. Current apps still use ad-hoc macOS signing and are **not Apple-notarized**; the updater does not establish Developer ID, notarization, stapling, or Gatekeeper acceptance. Validate a real installed-app upgrade separately before claiming that end-to-end installation has passed.

## Publish and recover

Use **Actions → Publish macOS universal prerelease → Run workflow** on `main` to request a release before the next 14:00 check. Manual and automation-triggered runs use the same version and verification rules. The workflow serializes release runs; a delayed run targeting a commit already covered by a newer published release is a no-op. New commits merged after a run takes its snapshot wait for the next run.

After verifying the build, the workflow creates a lightweight Git tag through GitHub's refs API at the selected `main` commit, without force-moving any existing tag. It then creates a draft Release only for that verified tag, uploads the eight distribution assets without overwriting existing files, and reads their digests and sizes back from GitHub. The set is the DMG, ZIP, updater archive, updater signature, `latest.json`, `SHA256SUMS.txt`, `BUILD-INFO.json`, and `INSTALL.zh-CN.txt`. It publishes the prerelease only when the complete set matches the verified build. A matching **empty** draft or a tag left behind before draft creation can be retried when its tag still points to the exact planned `main` commit. If any draft asset was already uploaded, or an unfinished draft's tag targets a different commit, preflight stops before another Mac build: rebuilding creates new timestamps and cannot safely reuse the old asset checksums. Inspect the draft and its original Actions run, then manually complete or clean up that draft and its tag before requesting another run. The automation never deletes or replaces draft assets. No DMG, ZIP, or other release binary is committed to Git.

Each public prerelease is currently ad-hoc signed and **not Apple-notarized**. The README and installation guide disclose this limitation. Developer ID signing, notarization, and stapling remain separate work; do not describe these trial builds as notarized or as a final macOS distribution.

If a release fails, inspect its Actions run, tag, and draft before rerunning. A tag left behind before draft creation can be reused only at the same selected `main` commit; a tag pointing elsewhere blocks publication. An empty draft for an older source commit can be resumed by rerunning that original Actions run. For a partially uploaded draft, decide explicitly whether to finish publishing from the original verified artifact or remove the unfinished draft and associated tag before starting a fresh run; do not delete or overwrite assets merely to hide a mismatch. The successful release build is an Actions artifact for diagnosis; the verified GitHub Release assets are the user downloads.

The 14:00 trigger is a local Codex automation attached to the maintainer's task, not a GitHub-hosted schedule stored in this repository. The maintainer's Mac must be powered on with the ChatGPT desktop app running ([Scheduled tasks](https://learn.chatgpt.com/docs/automations)), and GitHub authentication must be available. If the automation does not dispatch the workflow, use the manual workflow after checking the Actions status. No commit is lost from the next successful batch because the range always starts at the last published Release.
